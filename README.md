# 日本株スクリーニング自動化 - 仕様

**目的**: 日本株の銘柄をスクリーニングする

## 技術構成

- 言語/環境: Python、`uv`でプロジェクトごとに依存関係管理
- プロジェクト場所: `03_projects/python/jp-stock-screener/`（作成済み）
- データ取得: `yfinance`（導入済み）
- データ処理: `pandas`（導入済み）
- 出力先: ローカル保存（CSV）に加え、ダッシュボードはStreamlit Community Cloudにデプロイ済み（GitHubリポジトリ作成済み、そこと連携してデプロイ）
- 定期実行: Mac miniの`LaunchDaemon`で実行する方針に決定（詳細は「定期実行の方針」セクション参照）
- 通知: Discord Webhookで日次ジョブの結果を通知（詳細は「通知（Discord Webhook）」セクション参照）

## 流動性フィルタの仕様

- 売買代金 = 終値（Close）× 出来高（Volume）
- 10日移動平均・10日中央値の両方を算出（中央値を採用基準、平均は参考値）
- 除外基準: 10日中央値売買代金が1億円未満
- 取得期間: `period="1mo"`（10日移動平均に十分な日数）
- 20日ではなく10日を採用した理由: 流動性フィルタは直近の動向を反映したいため、より反応の早い10日窓を選択

## 対象銘柄の全体拡大（東証全銘柄）

- 銘柄マスタ: JPX公式サイトが配布する上場銘柄一覧（`data_j.xlsx`）を`fetch_universe.py`でダウンロードし、`universe.csv`に保存（銘柄コード、銘柄名、市場区分、33業種区分、ticker）
- 対象市場: プライム（内国株式）・スタンダード（内国株式）・グロース（内国株式）の合計3,707銘柄（2026年8月末時点）。ETF・ETN、REIT、PRO Market、外国株式は対象外
- バッチ処理: yfinanceへの一括リクエストは失敗しやすいため、200銘柄ずつに分割し、バッチ間に2秒の待機を挟んで取得（`screening.py`）
- 取得失敗の扱い: 失敗した銘柄は`failed_tickers.txt`に記録しスキップ（3,707銘柄中8銘柄が失敗。うち1件は社債型種類株式など特殊な銘柄でyfinance非対応は妥当と判断）
- 実行結果（2026年9月時点）: 取得成功3,699銘柄、流動性基準未達で除外2,181銘柄、フィルタ通過1,518銘柄

## 日次・月次のジョブ分割（終値の蓄積）

最終的なスクリーニングには日々の終値の蓄積が必要になるが、フィルタ判定（流動性など）まで毎回全銘柄を再計算するのは無駄が多いため、頻度で役割を分けている。

- **月次**（新規上場・上場廃止の反映、流動性フィルタの見直し）
  - `fetch_universe.py`: JPX公式データから`universe.csv`を再生成
  - `screening.py`: 更新された全銘柄で`period="1mo"`のデータを取得し、流動性フィルタ（10日中央値売買代金）を再計算、`screening_result.csv`に保存
  - 手順: `fetch_universe.py` → `screening.py` → `backfill_history.py`（新たに流動性フィルタを通過した銘柄の過去1年分を補完。下記「データ蓄積の前提」参照）→ `monthly_log.py`（更新前のcommitと比べ、除外・追加・名称や市場区分の変更・流動性フィルタの変化を`monthly_log.md`に追記）→「メモ」欄に手作業・気づいたこと・翌月への積み残しを追記 → commit＆push。`screening.py`まで実行しないと新規上場銘柄がスクリーニング対象に入らない点に注意。作業前に前月の「メモ」の積み残しを確認する。開始のきっかけは日次のDiscord通知（JPX一覧が手元の`data_j.xlsx`より新しくなると、月次更新を促す1行が付く）
  - 記録は`monthly_log.md`に残す（初回は2026-10-09。それ以前は2026-09-21の初回作成のみ）
- **日次**（終値・出来高の蓄積）
  - `daily_update.py`: `universe.csv`の全銘柄を対象に、OHLCV（Open/High/Low/Close/Volume）を`period="5d"`で取得し、取得できた全営業日分を保存（当初は最新行のみ保存していたが、実行漏れの日がそのまま欠損として残るため2026年9月に変更。直近5日以内の実行漏れなら次回実行で自動補完され、取引時間中に取得した暫定値も次回実行で確定値に上書きされる）
  - 結果を`daily_ohlcv.csv`（long形式: `date, ticker, open, high, low, close, volume`）に追記。同一日付・銘柄の組み合わせは上書きし重複を防止
  - ファイルは月単位で分割せず、単一ファイルに追記し続ける方針（新規上場・廃止は行の増減として自然に吸収されるため）
  - 当初はClose/Volumeのみ`daily_close.csv`/`daily_volume.csv`に分けて保存していたが、将来的なローソク足チャート描画には四本値（OHLC）が必要なため`daily_ohlcv.csv`に統合。yfinanceは元々OHLCVを一括取得しているため追加の取得コストは発生しない
  - 保存形式はlong形式（date, ticker, 値）を採用。wide形式（dateを行・tickerを列）は移動平均計算などで直感的だが、銘柄の新規上場・上場廃止のたびに列を追加・NaN埋めしてファイル全体を書き直す必要があり、月次で銘柄入れ替えがある本プロジェクトの運用と相性が悪いため見送り。分析時に必要ならその都度`pivot`でwide形式に変換する方針
  - 初回実行結果（2026年9月時点）: 取得成功3,704銘柄、失敗3銘柄（`daily_failed_tickers.txt`）
  - 取得失敗の分類（2026年10月変更）: 当初は「最終日の終値が取れなかった銘柄」をすべて取得失敗として数えていたが、18:00時点で当日分が未反映なだけの銘柄（出来高の少ない銘柄が中心）まで含まれ、失敗数が実態より多く見えていた。「5日間すべて取得できず（上場廃止・売買停止の可能性）」と「最終日のみ未反映（次回実行で自動補完）」に分けてログと`daily_failed_tickers.txt`に出力し、前者はDiscord通知でも警告する（失敗0件の日もファイルを書き出し、古い内容が残らないようにした）

## スクリーニング条件（流動性フィルタ後のランキング）

流動性フィルタ通過後、さらにTOPIXに対する相対強度（Relative Strength）でランキングし上位を抽出する。条件を後から変更・追加できるよう、各条件を`filters.py`の独立した関数として定義し、`run_screening.py`で組み合わせる構成にしている。

- **ベンチマーク**: TOPIX指数自体（`^TOPX`, `998405.T`）はyfinanceで404となり取得不可だったため、TOPIX連動ETFの`1306.T`（NEXT FUNDS TOPIX連動型上場投信）を代替として採用
- **相対強度の算出方法**: 個別銘柄とTOPIX ETFの21営業日騰落率の差（個別銘柄の騰落率 − ベンチマークの騰落率）。IBD式RSレーティングのような複合期間の加重平均は複雑なため見送り、まずはシンプルな方式を採用
- **抽出基準**: 流動性フィルタ通過銘柄のうち、相対強度上位10%（当初5%で開始し、もう少し下位まで見たいとの要望で10%に拡大）
- **通知**: 日次ジョブ終了時に、前回から新規にランク入りした銘柄をDiscordへ通知（「通知（Discord Webhook）」セクション参照）
- **データ蓄積の前提**: 相対強度の計算には21営業日超のヒストリカルデータが必要なため、`backfill_history.py`で流動性フィルタ通過銘柄＋ベンチマークの過去分を一度だけバックフィルし、`daily_ohlcv.csv`に統合。以降は`daily_update.py`の日次更新で追随（ベンチマーク`1306.T`も日次取得対象に追加済み）。バックフィル期間は`2mo`→`3mo`→`1y`と段階的に拡大（週足表示や将来の長期EMAを見据えて、2026年9月時点で245日分、2025-09-18〜2026-09-18を蓄積。ファイルサイズは27MB・37万行程度で、CSVのまま数年は問題ない見込み）
  - **月次更新で新たに通過した銘柄の補完**（2026-10-11追加）: バックフィルは当初9月時点の通過銘柄のみに行っていたため、10月の月次更新で新たに通過した87銘柄は日次蓄積開始（2026-09-16）以降の15日分しかなく、RSが計算できずランキングから黙って外れ、EMAも不安定でゴールデンクロスの誤検出（5銘柄）が出ていた。`backfill_history.py`を「流動性フィルタ通過銘柄のうち蓄積が200日未満の銘柄」だけを対象にし、既存行は上書きしない（`append_dedup(keep="first")`）よう変更。ベンチマーク`1306.T`は対象外（手動修正した異常値を上書きしないため）。実行の結果、109銘柄・19,830行を追加し、RSランキングは146→155銘柄、ゴールデンクロスは87→82銘柄になった。蓄積が200日未満のまま残るのは1年以内の新規上場銘柄（Yahoo Finance側にもデータがない）で、毎月対象に入るが取れる分だけ取って終わる
  - CSVの読み書きで浮動小数点の末尾の桁が変わることがある（例: `436.29998779296875` → `436.2999877929687`）。`append_dedup`の読み込み時の精度によるもので、値の差は無視できる
- **ファイル構成**:
  - `storage.py`: CSVへの重複除外追記処理を共通化（`daily_update.py`と`backfill_history.py`で共用）
  - `filters.py`: `liquidity_passed_tickers()`（流動性フィルタ通過銘柄の抽出）、`load_close_wide()`（daily_ohlcv.csvをwide形式にpivot）、`relative_strength()`（相対強度の計算、単一時点）、`relative_strength_series()`（相対強度の時系列、ダッシュボードのチャート用）、`relative_strength_wide()`（全銘柄・全日付の相対強度）、`above_ema_wide()`（終値がEMAより上か）、`sector_breadth()`（条件を満たす銘柄の割合を業種別・日付別に集計）。後ろ3つはダッシュボードの「業種別」タブ用
  - `run_screening.py`: 上記を組み合わせて実行し、`rs_ranking.csv`に出力
- 実行結果（2026年9月時点）: 流動性フィルタ通過1,518銘柄中、相対強度計算成功1,517銘柄（1銘柄はデータ欠損）、上位10%（151銘柄）を抽出

## スクリーニング条件（ゴールデンクロス・初動検知）

RSが「今強い銘柄」を捉えるのに対し、「上昇に転換した初動」を捉える条件として、5EMAが25EMAを下から上に抜けるゴールデンクロスを追加。`filters.py`に条件を関数として追加する設計のおかげで、既存のRS条件に影響を与えずに追加できた。

- **判定方法**: `filters.py`の`golden_cross_tickers()`。短期EMA（5日）と長期EMA（25日）の差分を計算し、前日は差分が0以下・当日は0超になった日を「クロス発生日」として検出
- **対象母集団**: 流動性フィルタ通過銘柄（RSランキングと同じ）
- **検出範囲**: 直近3営業日以内にクロスが発生した銘柄（日次実行のタイミングのズレを考慮した余裕）
- **既知の制約**: データ蓄積期間が短いとEMAの「立ち上がり」段階で価格に敏感に反応し、通常より多めにクロスを検出する傾向がある（2026年9月時点、1,518銘柄中252〜261銘柄を検出、やや多め）。データ蓄積が進むにつれて精度が上がる見込み
- **出力**: `run_golden_cross.py`を実行し`golden_cross.csv`（ticker, クロス日, 銘柄名, 業種）に保存
- **検証結果**（2026年10月）: 過去データで検証したところ、ゴールデンクロスはシグナル後の成績が全銘柄の平均とほぼ変わらず、初動を捉える効果はほとんど見えなかった。パーフェクトオーダーへの新規転換の方が有効（「シグナルの検証（`analysis/`）」参照）

## スクリーニング条件（パーフェクトオーダー転換・初動検知）

ゴールデンクロスより「RSが強い状態に入る初動」を安定して捉えられることを過去データで確認したため（「シグナルの検証（`analysis/`）」参照）、パーフェクトオーダー（5EMA > 25EMA > 75EMA）への新規転換を追加（2026年10月）。

- **判定方法**: `filters.py`の`fresh_perfect_order_tickers()`。パーフェクトオーダーが成立した日のうち、直前20営業日（`PO_FRESH_DAYS`）にパーフェクトオーダーでなかったものを「新規成立」とし（短い中断からの再成立は、検証で初動としての効果がなかったため除く）、さらに成立日のRSがプラスのものに絞る。RSは初動のトリガーというより、トレンド転換の結果として強くなるものとして補助的に使う
- **関連する関数**: `perfect_order_wide()`（パーフェクトオーダーの成立有無）、`fresh_perfect_order_wide()`（新規成立日）。定義は`analysis/signal_study.py`の「PO新規+RSプラス」と同じ
- **対象母集団**: 流動性フィルタ通過銘柄。銘柄ごとにデータ開始から63営業日（`EMA_WARMUP_DAYS`）はEMAの助走期間として判定しない（過去データの短い新規通過銘柄は、データが貯まるまで対象外）
- **検出範囲**: 直近5営業日以内（`PO_LOOKBACK`）。新規成立は1日約8件のため、ゴールデンクロスの3日より広げている
- **出力**: 日次ジョブで`run_perfect_order.py`が`perfect_order.csv`（列は`ticker, po_date, relative_strength, 銘柄名, 33業種区分`。`relative_strength`は最新のRS）を書き出し、Discord通知に使う（2026-10-17追加）。該当0件の日もヘッダー行だけのCSVを書き出す。ダッシュボードの「PO転換」タブはCSVを使わず毎回計算して表示する（`load_perfect_order()`。同じ関数で判定するため結果は一致する）
- **ダッシュボードでの位置**: 優先的に見たいためゴールデンクロスの左に配置。ゴールデンクロスのタブは当面見比べのために残す

## ダッシュボード（`dashboard.py`）

既存の`sector-rotation-dashboard`と同じ構成（Streamlit + Plotly）で、スクリーニング結果を閲覧するダッシュボードを実装。

- **タブ構成**: 「RS上位」「PO転換」「ゴールデンクロス」「業種別」「業種俯瞰」「業種内候補」の6タブ。前の3タブはそれぞれ独立したリスト+チャートの組み合わせで、`render_screening_tab()`として共通化（条件が増えてもこの関数を呼び出すだけで追加可能）。残りの3タブは構成が異なるため、それぞれ`render_breadth_tab()`・`render_sector_overview_tab()`・`render_sector_candidates_tab()`で描画
  - 選択中のタブだけを実行する（`st.tabs(..., key="main_tab", on_change="rerun")`と各タブの`.open`、2026年10月変更）。Streamlitは既定で選択されていないタブも含め全タブを毎回描画するため、ミニチャートの多いタブを追加すると全操作が重くなるのを避けるため。タブを行き来しても行の選択や業種の選択などの状態は保たれることをブラウザで確認済み
  - 選択ボックスはすべて`filter_mode=None`で文字入力による絞り込みを無効にしている（入力は想定しておらず、選択時にカーソルが点滅するのが気になったため）
- **リスト選択**: `st.dataframe`の`on_select="rerun"` + `selection_mode="single-row"`で行クリックによる選択に対応（デフォルトの`st.dataframe`は表示専用のため明示的な設定が必要だった）。列順は「業種 → 銘柄名 → ticker → RS(%)／クロス日」（PO転換タブは「… → ticker → PO成立日 → RS(%)」、2026年10月変更）。リスト欄は画面幅の1/3と狭く右側の列が隠れるため、どの業種が上位に多いかをざっと確認できるよう業種を常に見える左端に置いている（隠れる右側の列は横スクロールで確認する）
- **TradingView用リストのダウンロード**（2026年10月追加）: 「RS上位」「PO転換」「ゴールデンクロス」の各タブで、リストの下の`st.download_button`から銘柄リストを.txtでダウンロードできる。形式はTradingViewのウォッチリストの「リストをインポート」で読み込める`TSE:7203,TSE:6758,...`（取引所:コードのカンマ区切り、並び順はダッシュボードのリストと同じ）。英字入りの新コードも`TSE:153A`のようにそのまま出力し、インポートできることを確認済み。ファイル名は`rs_top_YYYYMMDD.txt`／`perfect_order_YYYYMMDD.txt`／`golden_cross_YYYYMMDD.txt`（データ基準日）。`on_click="ignore"`でダウンロード時にアプリを再実行しないようにし、選択中の銘柄やチャートを保つ（`to_tradingview_watchlist()`で変換）
- **チャート内容**（`render_chart()`で共通化）:

## データ品質の問題と対応（ベンチマークの異常値）

2026年4月末〜5月頭にかけて、ほぼ全銘柄でRSが-970%前後という明らかな異常値が発生。複数の無関係な銘柄で同時期に同程度の異常値が出ていたことから、個別銘柄ではなくベンチマーク側の問題と特定。

- **原因**: ベンチマーク`1306.T`のyfinanceデータで、2026-03-30・03-31の2日間だけ終値が約37円（前後の日は375〜382円、約1/10.2）という異常値になっていた。RSの21営業日窓の比較対象としてこの異常値が使われ、4月末〜5月頭の計算に混入していた
- **切り分け**: `yf.download`の再取得、`auto_adjust=False`での取得のどちらでも同じ異常値が返り、分割・配当イベントの記録もなかったため、Yahoo Finance側のソースデータ自体の欠損と判断（yfinance側のバグや設定ミスではない）
- **対応**: 正しい値の取得ができないため、前後の営業日（2026-03-27, 2026-04-01）から線形補間した値で`daily_ohlcv.csv`の該当2日分を手動修正。修正後、異常値は解消（-970%前後 → 通常範囲の16〜49%程度）を確認
- **今後の懸念**: 同様の孤立した異常値が他の銘柄にも潜んでいる可能性がある。現状は個別に気づいた都度対応する方針だが、頻発するようなら`load_close_wide()`への汎用的な異常値検出・除去ロジックの追加を検討

## データ品質の問題と対応（分割・配当落ちによる段差）

2026-10-19、検証用に過去データを取り直そうとした際に、`daily_ohlcv.csv`の価格に分割・配当落ちによる段差があることが分かった（ダッシュボードのチャートの崖には以前から気づいていたが、原因を調べていなかった）。

- **原因**: yfinanceの価格は取得時点で分割・配当を調整した値（`auto_adjust=True`）。`daily_update.py`は直近5営業日を取り直して上書き（`keep="last"`）するため、分割・配当落ちの日に過去の価格が調整されても、5営業日より前の行は調整前のまま残る。2026-09-29（9月末の配当落ち日で、10/1発効の分割も多い）の実行では、連休（9/21〜23）を挟んだ5営業日＝9/18〜9/29だけが調整後の値に置き換わり、**9/18を境に段差**ができた
- **影響**: 流動性フィルタ通過銘柄のうち、分割した45銘柄（8035.Tは1→5、8766.Tは1→15など）で9/18に-50〜-95%の見かけの暴落。RSは-70%前後になりRS上位に入らず、25EMA・75EMAが引きずられてPO転換も判定されない状態だった。配当落ちの786銘柄でも9/18に1〜3%の見かけの下落があり、パーフェクトオーダーが一時的に崩れたことになって、回復時に「新規成立」と誤検出されていた（10/16時点のPO転換40銘柄のうち14銘柄。10/17のテスト通知に出た大末建設など）
- **一括修正**: `repair_ohlcv.py`で流動性フィルタ通過銘柄（1,564銘柄）の全期間を取り直し、各銘柄が持っている期間だけを置き換えた（行数は変わらない）。ベンチマーク`1306.T`は手動修正した異常値（「ベンチマークの異常値」参照）があるため対象外（yfinance側は2026-03-30・31がまだ異常値のまま）。修正後、直近5日を取り直したときのずれ0件、9/18に30%超下落する通過銘柄0件を確認。修正前のファイルは`daily_ohlcv.csv.bak`（git管理外）。調整後の値は小数の桁が増えるため、行数は同じでファイルは33.8MB→38.4MBになった
- **修正後のスクリーニング**（10/16のデータ）: RS上位155銘柄（13銘柄入れ替え）、ゴールデンクロス180→175銘柄、PO転換40→36銘柄（誤検出14銘柄が外れ、分割の段差で判定から漏れていた6622.Tなど10銘柄が入った）
- **再発防止**: `daily_update.py`で、取得した5日分と保存済みの終値を同じ日付で比べ、0.5%以上ずれた銘柄（過去の価格が調整された銘柄）は全期間を取り直して置き換える（`ohlcv.py`の`mismatched_tickers()`・`replace_history()`）。対象は流動性フィルタ通過銘柄のみで、ベンチマークは警告だけ出す。配当落ちの日（3月末・9月末）は数百〜2,000銘柄が対象になり、取得に数分余計にかかる見込み
- **残っている課題**:
  - `backfill_history.py`は既存行を優先する（`keep="first"`）ため、月次更新で新たに通過した銘柄を補完すると、既存の行（日次取得分）と補完した古い行の調整がずれて段差が残りうる。`replace_history()`を使う形に変える
  - 流動性フィルタを通過しない銘柄の段差は直していない（スクリーニングに使わないため。通過しない銘柄にはyfinanceの値が壊れた銘柄もある: 7183.T・7082.Tは一部の日の終値が8億円台）
  - yfinance側の元データに1日-40%超の下落がある通過銘柄が3つ（8303.T: 2025-12-18に終値0、5537.T: 2025-09-30に-75%、8227.T: 2026-02-18に-66%）。原因は未確認

## 定期実行の方針

`daily_update.py`（および月次の`fetch_universe.py`/`screening.py`）を自動実行する方式として、GitHub Actionsではなく**Mac miniの`LaunchDaemon`**を採用することに決定。

- **比較した選択肢**: GitHub Actions／ローカルのlaunchd（Mac mini）／VPS常時cron／サーバーレス（AWS Lambda等）／PythonAnywhere等のPaaS
- **launchdを選んだ理由**: 常時稼働のMac miniが既にあるため、GitHub Actionsの最大の利点（「自分のPCが起きていなくても実行できる」）が意味を持たない。一方でGitHub Actionsはランナーが使い捨てのため、`daily_ohlcv.csv`への追記結果をgit commit＆pushで書き戻す仕組みが別途必要になり、その分セットアップの手間が増える。launchdなら今のローカル運用のコード・データの持ち方を一切変えずに済む
- **LaunchAgentではなくLaunchDaemonを採用する理由**: `LaunchAgent`はGUIログインセッションが必要だが、`LaunchDaemon`はログイン状態に関係なく動作する。今回のジョブは画面表示が不要なバックグラウンド処理なので、Mac miniのログイン状態を気にしなくて済む`LaunchDaemon`の方が適している（実行ユーザーは`plist`の`UserName`キーで指定する）
- **Streamlit Cloudとの連携**: ダッシュボードはGitHubリポジトリと連携してStreamlit Community Cloud上にデプロイ済み。ダッシュボードが参照するCSVはリポジトリ内のものなので、Mac miniで`daily_update.py`を実行した後は**git commit＆pushまで自動化する**必要がある（LaunchDaemonから呼ぶスクリプト内に組み込む想定）
- **開発体制**（2026年9月27日変更）: データの取得・更新を常時稼働のMac miniで行うことになったため、開発もマシンごとに役割を分ける
  - **データ取得・スクリーニング系**（`daily_update.py`, `backfill_history.py`, `ohlcv.py`, `repair_ohlcv.py`, `run_screening.py`, `run_golden_cross.py`, `run_perfect_order.py`, `filters.py`, `scripts/`）: Mac miniで開発する。実データ・実行環境（LaunchDaemon）がその場にあり検証しやすいため。MacBook Airで開発すると、動作確認が翌営業日18:00の定期実行を待つことになり効率が悪い
  - **通知**（`notify.py`、手順12）: Mac miniで開発する。日次ジョブ（`scripts/daily_job.sh`）の末尾に組み込まれており、実データでの送信テストもMac miniでしか行えないため

  - Mac miniでの開発時の注意: 日次ジョブは開発と同じ作業ツリーで動く。平日18:00の時点で`develop`以外のブランチにいたり、コードに未commitの変更があったりすると、意図しないブランチへのcommitや書きかけのコードの実行が起こりうる。18:00前後は`develop`にいて、コードの変更はcommit済みにしておく（`daily_job.sh`冒頭への安全チェック追加を検討中）

## 通知（Discord Webhook）

日次ジョブの結果をDiscordへ通知する（`notify.py`、2026年9月追加）。

- **方式の選択**: Discordプラグイン（Claude Codeのチャンネル機能）はClaude Codeセッションの起動中しか動かず、LaunchDaemonからの無人実行には向かないため、Discord Webhookへ直接POSTする方式を採用。標準ライブラリ（`urllib`）のみで実装し依存関係の追加なし
- **成功時**: RS上位・PO転換それぞれの総数と、前回から**新規に入った銘柄**（各最大10件、超過分は「…ほか○銘柄」）、ダッシュボードのリンク（`<>`で囲みリンクプレビューを抑止）を通知。あわせてJPXの上場銘柄一覧（`jpx.py`）をダウンロードして基準日を手元の`data_j.xlsx`と比べ、新しければ月次更新を促す1行を加える（月次更新するまで毎日表示。JPXにアクセスできない場合は1行を省いて通常どおり通知）
- **新規判定**: `daily_job.sh`が`git pull`直後のcommitを`BASE_REF`として記録し、そのcommit時点のCSV（`git show`）と今回のCSVを比較。前日の結果はcommit済みなので別途状態ファイルを持つ必要がない
- **失敗時**: `trap ERR`で失敗した行番号とexit codeを通知。通知自体の失敗ではジョブを失敗扱いにしない（`|| true`）
- **設定**: Webhook URLとダッシュボードURLは`.env`（git管理外、権限600）に記載。GitHubにpushしているリポジトリのため、URLをコードに書かない
    ```
    DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/...
    DASHBOARD_URL=https://〇〇.streamlit.app
    DISCORD_MENTION_USER_ID=...  # 任意。自分のDiscordユーザーID（下記「スマホに通知が届かない件」参照）
    ```
- **動作確認**: `uv run python notify.py success --base <git ref> --dry-run`で送信せずに通知文を表示できる
- **1メッセージの文字数**: Discordの上限（2000文字）を超える場合は切り詰める（通常は700文字程度）
- **スマホに通知が届かない件**（2026年10月7日解決）: 実際にはスマホに通知は届いていたが、Discordのアプリアイコンのバッジは自分宛てのメンションとDMしか数えないため、Webhookの投稿ではバッジが付かず見落としていた。対策として、`.env`に`DISCORD_MENTION_USER_ID`（自分のDiscordユーザーID）を設定すると通知の先頭に自分宛てのメンションを付けるようにした（`allowed_mentions`で対象を自分だけに限定）。未設定ならメンションなしで送信する。テスト送信でバッジが付くことを確認済み（調査の過程で、iOSの集中モード・時刻指定要約、ブラウザでのDiscord表示中のプッシュ抑止は原因でないことを確認）
- **通知のゴールデンクロスをPO転換に置き換え**（2026-10-17実施、Mac miniで作業）
  - **背景**: 過去データの検証で、ゴールデンクロスは初動を捉える効果がほとんどなく、パーフェクトオーダーの新規転換（PO転換）の方が有効だった（「シグナルの検証（`analysis/`）」参照）。ダッシュボードには「PO転換」タブを実装済み（2026-10-17）。通知もPO転換を見たい

  - **通知の書式**: 見出しは`**PO転換**: {件数}銘柄（新規 {新規件数}）`、各行は`・{ticker} {銘柄名}（{33業種区分}）{po_date} RS {relative_strength:+.1%}`。最新日の終値が未反映の銘柄はRSが計算できず空欄になるため、`RS -`と表示する（`notify.py`の`format_rs()`。ダッシュボードのPO転換タブでも同様に空欄になる）
  - **確認結果**（2026-10-17、データ基準日2026-10-16）: `run_perfect_order.py`で40銘柄を検出し、ダッシュボードの`load_perfect_order()`と同じ処理の結果と件数・銘柄・並び順が一致。0件時にヘッダー行だけのCSVになること、`--dry-run`の通知文、Discordへのテスト送信（先頭に「テスト送信」の1行を付けて手動送信）で表示に問題がないことを確認
  - **初回の「新規」の扱い**: 実施日に`perfect_order.csv`もcommitしたため、2026-10-19(月)の日次ジョブから、その日に新しく成立した銘柄だけが「新規」として通知される見込み（commitしていなければ初回は全件が新規になっていた）
  - **実施した手順**（記録として残す）:
    1. 作業前にMac miniで`git pull`する（判定の関数はMacBook Airで`filters.py`に追加済み）
    2. `run_perfect_order.py`を新規作成する。`run_golden_cross.py`と同じ形で、判定に`filters.py`の`fresh_perfect_order_tickers(tickers, close_wide)`（戻り値は`{ticker: 成立日}`、直近`PO_LOOKBACK`=5営業日の新規成立かつ成立日のRSがプラス）を使う。出力は`perfect_order.csv`で、列は`ticker, po_date, relative_strength, 銘柄名, 33業種区分`。`po_date`は`%Y-%m-%d`の文字列、`relative_strength`は最新のRS（`filters.py`の`relative_strength(tickers, close_wide)`の値。ダッシュボードの`load_latest_rs()`と同じ）、銘柄名・業種は`universe.csv`から付ける。並びは`po_date`の新しい順、同日は`relative_strength`の高い順（ダッシュボードの`load_perfect_order()`と同じ）。該当0件の日もヘッダー行だけのCSVを書き出す（`notify.py`が読めるように）。`run_golden_cross.py`は該当0件だと列のない空のDataFrameを書き出すため、ヘッダーのない空ファイルになる。同じ書き方をまねず、`pd.DataFrame(rows, columns=["ticker", "po_date", "relative_strength", "銘柄名", "33業種区分"])`のように列名を明示する
    3. `scripts/daily_job.sh`: `uv run python run_golden_cross.py`の次の行に`uv run python run_perfect_order.py`を足し、`git add`の対象に`perfect_order.csv`を加える
    4. `notify.py`の`build_success_message()`: ゴールデンクロスの部分（`new_entries("golden_cross.csv", base)`とその表示）を`perfect_order.csv`に置き換える。見出しは`**PO転換**: {件数}銘柄（新規 {新規件数}）`、各行は`・{ticker} {銘柄名}（{33業種区分}）{po_date} RS {relative_strength:+.1%}`（RS上位の行と同じ書式）。新規の判定（`new_entries()`）と表示件数の上限（`MAX_ITEMS`=10）は既存の仕組みをそのまま使う
    5. 確認: `uv run python run_perfect_order.py`で`perfect_order.csv`を作り、`uv run python notify.py success --base HEAD --dry-run`で通知文を確認する（送信はしない）。ダッシュボードのPO転換タブと銘柄数・銘柄が一致することも確認する
    6. commit＆pushし、READMEを更新する（この「今後の作業」の項目、上の「成功時」の項目、「スクリーニング条件（パーフェクトオーダー転換・初動検知）」の「出力」の項目）
  - **注意**: 新規になるのはその日に新しく成立した銘柄（1日約8件）だけの見込み。PO転換の銘柄は成立から5営業日リストに残るため、同じ銘柄が新規として通知されるのは成立日の1回だけ
